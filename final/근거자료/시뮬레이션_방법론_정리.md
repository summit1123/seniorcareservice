# 시뮬레이션 방법론 — 3번 답변 정리 (8번과 세트)

> 심사 지적(7/24 3번): 시뮬레이션에 생활권 정보가 반영돼 있는가. 보고서의
> 'data'라는 표현이 raw data로 오인될 소지가 있다. 가상 데이터 사용이 문제없는지,
> "시나리오 설계 자체가 유리한 결과를 유도한 것 아니냐"에 답할 논리를 마련할 것.
>
> **3번과 8번은 한 몸이다.** 3번은 "어떻게 만들었나", 8번은 "그렇게 만든 것으로
> 왜 검증이 되나". 발표에서도 이어서 말하는 편이 자연스럽다.

---

## 0. 먼저 범위를 좁힌다 — 이 답변의 뼈대

가장 흔한 실수는 "저희 데이터는 현실적입니다"라고 방어하는 것이다. 그건 방어가
안 된다. 우리가 만든 데이터이기 때문이다. **답은 반박이 아니라 범위 인정이다.**

> **시뮬레이션이 증명하는 것은 하나뿐입니다 — 코드가 저희가 선언한 규칙대로
> 작동한다는 것. 규칙이 타당한지는 시뮬레이션이 아니라 문헌과 계리 원리로 따로
> 답변드립니다. 예측력은 주장하지 않습니다.**

이렇게 먼저 좁히면 8번 지적("설계대로 예쁘게 나온 것 아니냐")이 **이미 인정한
것**이 되어 공격력을 잃는다. 그리고 무게가 시뮬레이션에서 **규칙 자체의
근거**(3일=Isaacman, eps=장소인식 문헌, 가중치=신뢰도 원리, AND=위치 중립)로
옮겨간다 — 그쪽이 우리의 진짜 방어선이다.

---

## 1. 용어 교정 — 우리가 먼저 말한다

| 쓰지 않을 말 | 쓸 말 |
|---|---|
| data | **synthetic scenarios (합성 시나리오)** |
| "실제 드라이빙 로그를 바탕으로" | "문헌 기반 파라미터로 생성한 합성 시나리오" |
| 30명 | **180 시나리오** (6유형 60명 로스터 × 3환경) |

1차 자료의 "실제 드라이빙 로그를 바탕으로 6개 범주 및 30명"은 부정확했다 —
**실제 로그의 경험적 분포를 사용한 적이 없다.** 이 정정을 우리가 먼저 꺼낸다.

현재 실물: **80,032 트립 · 180 시나리오 × 14개월** (기준선 2개월 + 평가 12개월).

## 2. 생성 체인 4단계 — 무엇을 누가 만들었나

| 단계 | 누가 | 무엇을 | 재현성 장치 | 코드·산출물 |
|---|---|---|---|---|
| (a) 아키타입 정의 | **사람** | 문헌 3축(이동범위·만성 위험행동·패턴 변화)의 조합으로 6유형 | 파라미터 전량 코드 선언 | `personas.py` (6 아키타입) |
| (b) 이동 프로필 | **LLM** (gpt-4o) | 사람별 존 구성 — 장소·방향·비중·변화 시점 | 구조 계약 검증 통과본을 **1회 생성 후 고정 커밋** | `mobility_profiles.json` (60명, seed 26071406) |
| (c) 방문 이벤트 | **결정론 엔진** | 월별 방문·거리·이벤트 전개 | 시드 = `sha256(전역시드 \| driver_id \| month)` → **비트 동일 재현** | `engine.py`, `gaip_visit_events.csv` |
| (d) 위험 유형 분해 | 결정론 | TAAS 통계로 급제동·과속·급가속 비율 부여 | **표시 전용 — 판정 미진입** | 가중치 교체 후 180건 판정 diff 0 |

### LLM이 한 일과 하지 않은 일 (이 구분이 핵심)

- **한 일**: 생활권 프로필만 — 어떤 장소를 몇 대 몇 비중으로, 언제 변화가 오는지
- **하지 않은 일**: **임계값·가중치·판정 규칙을 정하지 않았다.** 전부 사람이 코드에
  선언한 값이다
- **재시도 조건**: JSON 구조 계약 위반일 때만, 최대 3회. **판정 결과는 재시도
  판단의 입력이 아니다** — "원하는 판정이 나올 때까지 돌리는" 구조가 성립하지 않는다
- **고정**: 통과본을 1회 생성해 저장소에 커밋했다. 이후 전 단계가 비트 단위로 재현된다

## 3. 왜 이 방식이 reasonable한가 — 라벨 차단

채점 함수는 **유형 라벨을 인자로 받지 않는다.** 코드에 입력 계약이 선언돼 있다
(`DEFAULT_PRODUCT_RULES["decision_feature_contract"]`).

**허용 입력 8개** (이것만 판정에 들어간다)
```
zone_available · data_coverage_pct · mileage_score · in_zone_safe_score
out_zone_safe_score · pattern_stability_score · mobility_change_index
risky_behavior_change_index
```

**생성 전용으로 차단된 7개**
```
archetype_id · designed_type · data_quality · visit_label
scenario_truth · expected_reward_state · expected_care_state
```

정답지(`expected_*`)와 유형 라벨(`designed_type`)이 명시적으로 배제돼 있고, UI
경계의 DTO는 제거 목록이 아니라 **허용목록(allowlist)** 방식이라 스키마가 늘어도
라벨이 샐 수 없다.

→ 그래서 검증 대상이 성립한다: **"설계 의도가 파이프라인을 통과해 실제로
발현되는가."**

## 4. 무엇이 검증됐나 — 그리고 무엇은 아닌가

**검증된 것** (전부 코드·데이터로 재현 가능)

| 확인 | 실측 |
|---|---|
| 나야 할 케이스가 난다 | 이동·위험 동시변화형 **케어 30/30 발동**, 규칙 위반 0 |
| 나면 안 되는 케이스가 안 난다 | 이동만 변화형 — 이동 임계 초과가 **평가 360개월 중 191개월**(최대 73.9%p)인데 **케어 0건** |
| 위치로 벌하지 않는다 | 생활권 안 위험행동형 안전점수 15.8점, **우대 0/30** (위치로 채점했다면 통과했을 것) |
| 환경이 달라도 판정이 같다 | 같은 사람 × 3환경 — 케어 60/60, 우대 56/60 일치 |
| 데이터가 부족하면 유보 | sparse 6건 전건 '보류', 요율 변동 0 |
| 상시 검증 | pytest **254**건(판정 계약 27) + JS **22**건 |

191개월/케어 0건이 이 항목의 최강 증거다 — AND 게이트가 OR였다면 191번 발동했다.

**검증되지 않은 것** (먼저 말한다)

- **예측력 없음** — 합성 데이터에 사고가 들어 있지 않으므로 사고율·손해율에 대해
  아무것도 말하지 않는다
- **파라미터 절대값은 설계값** — 월 방문 13~42회, 위험률 3%/72% 등은 방향성만
  문헌을 반영했다. 파일럿에서 실주행 경험분포로 대체한다
- **데이터의 현실성은 주장하지 않는다** — 주장하는 것은 로직 일관성뿐

## 5. 운용 결함도 공개한다

LLM 라벨이 44/60에서 동일 명칭으로 수렴하는 문제가 있었다. **고유 라벨 106건은
보존하고 중복 57건만 결정론으로 치환**한 뒤 판정 불변을 검증했다. 숨기지 않고
먼저 말하는 편이 신뢰에 낫다.

## 6. 발표 답변 (60~90초)

> "먼저 용어를 바로잡겠습니다. 저희가 'data'라고 말씀드린 것은 실주행 데이터가
> 아니라 **합성 시나리오**입니다. 1차 자료의 '실제 드라이빙 로그를 바탕으로'라는
> 표현도 부정확했습니다 — 실제 로그의 경험 분포를 쓴 적이 없습니다. 현재 규모는
> 6유형 60명 로스터를 3개 지역환경에 둔 **180 시나리오, 14개월, 80,032 트립**입니다.
>
> 생성은 네 단계입니다. 사람이 문헌 3축으로 6유형을 정의하고, LLM이 생활권
> 프로필을 만들되 구조 계약을 통과한 결과만 저장소에 고정합니다 — **임계와
> 가중치는 LLM이 손대지 않습니다.** 그다음 결정론 엔진이 시드를
> `sha256(전역시드·운전자·월)`로 고정해 방문 이벤트를 전개하고, 마지막으로 위험
> 이벤트의 유형 분해에만 TAAS 통계를 씁니다 — 이 값은 표시 전용이라 판정에
> 들어가지 않습니다.
>
> 그리고 저희가 시뮬레이션으로 주장하는 범위를 분명히 하겠습니다. **예측력은
> 주장하지 않습니다.** 저희가 보여드리는 것은 **코드가 선언한 규칙대로
> 작동한다**는 것 하나이고, 규칙 자체의 타당성은 문헌과 계리 원리로 따로
> 말씀드립니다.
>
> 그게 성립하는 이유는 채점 함수가 **유형 라벨을 아예 받지 않기** 때문입니다.
> 코드에 허용 입력 8개가 선언돼 있고 정답지와 유형 라벨은 명시적으로 배제돼
> 있습니다. 그래서 나야 할 케어 30건은 전부 나고, **나면 안 되는 케이스는 이동
> 지표가 360개월 중 191개월이나 임계를 넘었는데도 0건**입니다. 다만 방문 횟수·
> 위험률의 절대값은 설계값이며, 파일럿에서 실주행 경험분포로 대체하겠습니다."

## 7. 예상 후속질문

**"LLM이 만든 데이터면 LLM 편향이 들어가지 않나"**
→ LLM은 생활권 프로필(장소·방향·비중·변화 시점)만 만들고 임계·가중치는 정하지
않습니다. 구조 계약은 코드가 검증하고 위반일 때만 재생성하며(최대 3회), **판정
결과는 재시도 판단의 입력이 아닙니다** — 원하는 판정이 나올 때까지 돌리는 구조
자체가 성립하지 않습니다. 산출물은 1회 생성 후 고정 커밋이라 이후 전 단계가 비트
단위로 재현됩니다.

**"합성으로 검증했다는 게 무슨 의미가 있나"**
→ 예측력이 아니라 **로직 일관성**의 검증입니다. 실데이터가 확보되면 지금의 판정
계약 테스트 27건이 그대로 실데이터 검증 하네스가 됩니다.

**"시나리오 설계가 유리한 결과를 유도한 것 아닌가"**
→ 맞습니다, 결과는 설계의 산물입니다. 그래서 저희는 데이터의 현실성을 주장하지
않고, **엔진이 틀릴 수 있었던 지점에서 틀리지 않았는가**만 봅니다. 이동만 변한
케이스는 지표가 191개월 임계를 넘었고, AND 게이트가 깨져 있었다면 191번
발동했을 겁니다. 0건이었습니다.

**"30명에서 180으로 바뀐 이유는"**
→ 1차 이후 데이터 파이프라인을 재설계하며 로스터를 다시 짰습니다. 30명은 6유형에
유형당 5명이라 "나오면 안 된다"를 보여야 하는 대조군 셀이 얇았습니다. 유형당
10명으로 올리고 같은 로스터를 3환경에 배치하는 통제 비교를 더해 180이 됐습니다.
